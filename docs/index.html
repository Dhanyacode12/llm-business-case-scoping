APPLIED LLMS FOR BUSINESS CASES

Scoping vague “use AI” requests

Two scenarios: A3 Support Ticket Overload and B5 Executive Dashboard Automation

A3 · THE SCENARIO

Support tickets are piling up

1

Customer writes a ticket

Free text, any topic, any urgency

→

2

A person sorts it by hand

Slow and not always consistent

→

3

It reaches a team

Billing, account access, shipping…

Decision-maker: Head of Support Decision: which team, how urgent

Goal: faster answers. The AI helps the support staff. It does not replace them.

A3 · BEFORE ANY AI

First, find where the time is lost

Because a sorting model only helps if sorting is the slow part, we measure the three stages first. This step needs no machine learning.

A3 · THE DATA PROBLEM

Can we trust the old sorting records?

1

Take 100 tickets

From the past

→

2

Two support staff sort them

Each alone, without seeing the old record

→

3

Compare

How often do they agree?

They agree most of the time

The old records are usable as labels.

They often disagree

A model would learn the confusion. Don’t train on them.

A3 · THE PLAN

Discover categories first, then classify

STEP 1

Turn text into numbers

Similar meaning, similar numbers

→

STEP 2

Group similar tickets

Categories come from the data

→

STEP 3

Humans check the groups

With an “other” option

→

STEP 4

Train a router

Suggests a team for new tickets

Because there are no trusted labels, we find the categories before we predict them.

Not doing: AI replies to customers before sorting is proven · trusting the old records without testing them

A3 · METHOD: BERTOPIC + HDBSCAN

How grouping finds categories

Illustrative sketch. Each dot is one ticket. Not real data.

1. Similar tickets land close together.

2. Crowded areas become groups, and a person names them.

3. Odd tickets are left out, not forced into a group.

A3 · WHAT I LEARNED

From assumption to action

I ASSUMED

The old routing records are correct answers

→

SO I PLAN

Two support staff sort the same 100 tickets, then we compare

I WORRIED

An LLM would force tickets into wrong categories

→

SO I ADDED

An “other” option, and labelling without seeing the LLM’s suggestion

WRONG ASSUMPTION

Clustering and classification are the same

→

NOW I KNOW

Clustering finds categories. Classification sorts into categories that already exist.

B5 · THE SCENARIO

Explaining weekly KPI changes

Executives want an AI dashboard that explains why the numbers moved. “Explain” can mean three things:

FEASIBLE

Describe

What changed, and where

FEASIBLE

Flag

Is it unusual, or normal variation?

NOT FROM A DASHBOARD

Prove why

Needs an experiment

Decision-maker: executive team Decision: where to look and act each week

B5 · THE PLAN

Calculate first, then let the LLM write

STEP 1

Collect KPI numbers

With one agreed definition per metric

→

STEP 2

Split the change

By region, segment, channel

→

STEP 3

Check the normal range

Is it outside usual variation?

→

STEP 4

LLM writes the sentence

Only from the verified numbers

Because a cause can’t be proven from a dashboard, we calculate the facts and the LLM only puts them into words. This is mostly not machine learning.

Not doing: asking an LLM to explain raw data · claiming a cause without an experiment

B5 · STEP 3

Is this change unusual?

Illustrative sketch, not real data.

Compare each week with normal variation.

Most week-to-week changes are noise, and the dashboard should say so.

B5 · STEP 2 · METHOD: RATE / MIX

Where did the change come from?

Toy example with made-up numbers. The axis starts at 80.

Rate: people buy less in each group.

Mix: fewer customers are in the group that usually buys more.

The two reasons call for different actions, so the dashboard shows both.

B5 · STEP 4

How the dashboard should word it

AVOID: IT CLAIMS A CAUSE

“Sales fell because the campaign ended.”

USE: IT STATES FACTS ONLY

“Sales fell 8%. The campaign ended the same week. We haven’t tested whether it caused the drop.”

The LLM writes only what the numbers support, and it says what has not been tested.

B5 · WHAT I LEARNED

From assumption to action

I ASSUMED

A dashboard should tell executives the cause

→

NOW I KNOW

It can show what changed, not prove why. So we avoid the word “because”.

WRONG ASSUMPTION

When a number drops, customers changed their behaviour

→

NOW I KNOW

The customer mix can change instead. That is the rate and mix idea.

I did not use an LLM for the first draft. I used Claude afterwards to discuss it and to test my assumptions.

THE SHARED LESSON

The main work was framing

  • A3: ML fits, but we start by discovering categories
  • B5: mostly not ML. The LLM only writes up calculated numbers
  • In both: decide what is really being asked before building anything
