APPLIED LLMS FOR BUSINESS CASES

Scoping vague “use AI” requests

Two scenarios: A3 Support Ticket Overload and B5 Executive Dashboard Automation

A3 · SUPPORT TICKET OVERLOAD

Help staff route tickets faster, not replace them

The problem

Tickets arrive as free text and are routed by hand. Goal: route and prioritise faster, so response time drops.

First check, no ML

Where is time really lost: triage, the right team, or resolution? If routing isn’t the bottleneck, a routing model won’t help.

Problem type

No clean labels, no agreed categories. Unsupervised first to discover categories, then classification.

A3 · DATA AND RISKS

The data exists, but the labels can’t be trusted

What we have

  • Ticket text, timestamps, customer details
  • Routing history and agent replies
  • Response and resolution times
  • Labels: none we can trust

Top risks

  • Label noise: manual routing is inconsistent
  • Leakage: agent replies must not be inputs
  • Rare critical tickets: outages, legal, security

A3 · APPROACH

Discover categories first, then classify

1

Group

Group similar tickets. Support leads name the groups.

2

Label

An LLM suggests labels on a sample. Humans review, with an “other” option and some blind labelling.

3

Assist

Show agents similar past tickets.

Not doing: LLM auto-replies before triage is proven, or trusting the routing history as labels before testing it.

A3 · WHAT I LEARNED

An assumption became a test

Working with the LLM

  • I assumed routing history made good labels
  • Test: two agents route the same 100 tickets
  • I challenged LLM labelling: it may force wrong categories, so I added “other” and blind labelling

New method: BERTopic + HDBSCAN

  • Embeddings turn text into numbers
  • HDBSCAN groups similar tickets and leaves odd ones out
  • BERTopic names the groups
  • My wrong assumption: clustering is not classification

B5 · EXECUTIVE DASHBOARD AUTOMATION

“Explain a KPI change” can mean three things

FEASIBLE

Describe

What changed, and where.

FEASIBLE

Flag

Is the change unusual, or normal variation?

NOT FROM A DASHBOARD

Prove why

Needs an experiment or a causal design.

So this is mostly not ML. The LLM only writes up numbers that were calculated.

B5 · DATA AND RISKS

The danger is a confident, wrong explanation

What we have

  • KPI numbers over time
  • Breakdowns by region, segment, channel
  • Metric definitions, campaign and holiday calendars
  • Labels: none for “the reason”

Top risks

  • Unclear definitions across teams
  • Noise read as signal
  • Mix shift looks like behaviour change
  • The LLM invents fluent reasons

B5 · APPROACH

Calculate first, then let the LLM write

1

Split

Break each change down by region and segment.

2

Compare

Check against normal seasonal variation.

3

Write

The LLM turns verified numbers into plain text.

Not doing: asking an LLM to explain raw data, or claiming a cause without an experiment.

B5 · WHAT I LEARNED

A dashboard can show what changed, not prove why

Working with the LLM

I thought a dashboard should tell executives the cause. We settled on this wording:

“Sales fell 8%. The campaign ended the same week. We haven’t tested whether it caused the drop.”

New method: rate/mix

  • Rate: people buy less in each group
  • Mix: the customer mix shifted
  • My wrong assumption: a drop means behaviour changed

THE SHARED LESSON

The main work was framing

  • A3: ML fits, but start by discovering categories
  • B5: mostly not ML; the LLM only writes up calculated numbers
  • In both, decide what is really being asked before building anything
